Monitor Any API with a GitHub Action: fail the build when it breaks

Your parser, your scraper, your integration — most silently rot. A feed returns 5 records instead of 300, a field gets renamed, the endpoint 404s, and nothing tells you until a customer does. This is the 30-second, zero-infra way to turn that into a red CI run you actually see.

What “silently breaks” actually means

An API can be up and still wrong for your code. The four regressions that matter for a list-of-records endpoint — and the exact ones jobfeed-watchdog fingerprints on every run:

SignalWhat it catchesExample
Top-level container changelist → dict (or vice-versa)a response wrapper was added — data[“hits”] now data[“results”]
Record key-set diffa required field removed or renamedprice becomes price_usd — your code reads None
Record-count floorcount_ratio / min_countparser broke — returns 5 of 300 instead of the real set
Fetch / parse / HTTP errorfeed down or malformedthe endpoint 404s or returns HTML instead of JSON

You don’t need a test per field. You need a structural fingerprint — the shape of the data — compared to a known-good baseline, every run.

Step 1 — add the monitor (30 seconds)

Clone the action into any repo you already have — the one that runs your parser/scraper/integration is the natural home:

git clone https://github.com/earnnova-dev/jobfeed-watchdog
cd jobfeed-watchdog
cp -r watchfeed.py feeds.json .github/feeds-watcher.yml /path/to/your/repo

Or copy just the two pieces that do the work — watchfeed.py (the fingerprint engine) and the workflow — and skip the rest. The core is stdlib-only; JSON feeds need nothing installed in CI. YAML feeds are optional (they need pyyaml).

Step 2 — point it at your feeds

One file, one JSON object, one entry per endpoint you depend on. record_path is the dotted path to the list of records — leave it out when the response is the array. The rest of the fields are optional:

{
  "feeds": [
    {
      "id": "remote-jobs-api",
      "url": "https://remote-jobs-api.tten.no/v1/jobs",
      "record_path": "jobs",
      "count_ratio": 0.5,
      "min_count": 5,
      "timeout": 30
    }
  ]
}

Watch several at once by adding entries of the same shape:

{
  "feeds": [
    { "id": "hn-ai",      "url": "https://hn.algolia.com/api/v1/search?query=ai", "record_path": "hits", "min_count": 3 },
    { "id": "nyc-weather","url": "https://api.open-meteo.com/v1/forecast?latitude=40.7&longitude=-74.0", "record_path": "daily.temperature_2m_max", "min_count": 1 }
  ]
}
  • count_ratio — fail if this run’s record count drops below this fraction of the stored baseline (default 0.5: a 50% collapse trips it).
  • min_count — a hard floor, so an empty or nearly-empty feed always fails even on the first run.
  • timeout — seconds before a fetch is treated as down.

Step 3 — the workflow that fails your build

Drop this in .github/feeds-watcher.yml. It runs on a schedule (every 6 hours by default) and on manual dispatch, runs the fingerprinter against each feed, and turns the run red the moment one regresses — which is what GitHub Actions notifications (Slack / email / Discord) are built to page you about:

name: Feed Watchdog
on:
  schedule:
    - cron: "0 */6 * * *"   # every 6 hours on the hour (UTC)
  workflow_dispatch:

jobs:
  watch:
    runs-on: ubuntu-latest
    permissions:
      contents: write        # so it can commit a fresh baseline back when healthy
    steps:
      - uses: actions/checkout@v4

      - name: Check feeds
        id: check
        run: |
          python3 watchfeed.py feeds.json state || status=$?
          if [ -n "$status" ]; then
            echo "::error::Feed breakage detected (see report above)"
            exit 1
          fi

      - name: Commit new baseline (only when healthy)
        if: steps.check.outcome == 'success'
        run: |
          git config user.name "feed-watchdog"
          git config user.email "feed-watchdog@users.noreply.github.com"
          git add state || true
          if ! git diff --cached --quiet; then
            git commit -m "chore(watchdog): update baselines $(date -u +%Y-%m-%dT%H:%M:%SZ)"
            git push
          fi

The baseline commit is the subtle part: it only writes a new state/<id>.baseline.json when the feed is healthy. A broken feed never gets “blessed,” so the baseline stays the last-known-good shape and the run keeps failing until the upstream is fixed. That’s the whole trick — you’re diffing every run against the last healthy shape, automatically.

How it decides: the exit codes

The engine prints a per-feed report, then exits with a code the workflow can branch on:

CodeMeaningBuild result
0all feeds healthy (or none configured)green — baseline may refresh
1one or more feeds broke (schema / count / down)red — you get paged
2usage / config error (bad feeds.json, bad record_path)red — fix your config

Because it’s a plain non-zero exit, you can wire it into any pipeline that already fails on non-zero — no custom runner, no polling service, no paid uptime product.

When to use this vs. a paid uptime monitor

  • Use this when the failure that matters is your code’s contract with the feed — a renamed field, a collapsed list, a reshaped response. Uptime monitors can’t see your record_path; this can.
  • Use a paid monitor for 24/7 availability paging, multi-region probing, and status pages. They run on your schedule for free on GitHub Actions and cost nothing — but they don’t know what “the right shape” is for your data.
  • Use both — a health-check for “is it up” and this for “is it still shaped like I expect.”

Notes

  • Stdlib-only core (urllib); runs anywhere, no heavy installs in CI. YAML feeds are optional via pyyaml.
  • The fingerprints are deterministic and the pure functions are unit-testable with no network — you can extend the signals (new field, new container) without touching a live feed.
  • Schedule it to whatever cadence your feeds change at. 6 hours is the default; a per-minute monitor is fine for a canary but hammering rate-limited free tiers is how you get blocked.
