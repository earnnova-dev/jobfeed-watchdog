Catch silent API feed breakage before it hits your dashboard

A tiny, dependency-light GitHub Action that fails the build the moment a job feed — or any JSON/YAML endpoint returning a list of records — silently breaks: a schema change, a record-count collapse, or an outright outage.

Set it up in 30 seconds

Guide: fail the build when any API breaks →

The problem it solves

Feed consumers find out about breakage too late. A parser change quietly returns 5 records instead of 300, a required field disappears, or the upstream goes down — and nothing pages anyone until a dashboard goes blank or a user complains.

jobfeed-watchdog runs a structural fingerprint on every schedule and turns the GitHub Actions run red when something regresses, so your normal Actions notifications (email / Slack / Discord) fire automatically.

pip install jobfeed-watchdog Stdlib-only core (urllib) No server, no billing No secrets required JSON + optional YAML

Install & run (30 seconds)

Already on PyPI — install the stdlib-only CLI:

pip install jobfeed-watchdog
jobfeed-watchdog feeds.json /tmp/state     # fingerprint + fail on regression

Or copy the GitHub Action template into your repo (recommended for scheduled builds):

git clone https://github.com/earnnova-dev/jobfeed-watchdog
cd jobfeed-watchdog
cp -r watchfeed.py .github/feeds.json /path/to/your/repo

Then list the feeds you want watched in your repo’s feeds.json:

{
  "feeds": [
    {
      "id": "remote-jobs-api",
      "url": "https://remote-jobs-api.tten.no/v1/jobs",
      "record_path": "jobs",
      "count_ratio": 0.5,
      "min_count": 5,
      "timeout": 30
    }
  ]
}
  • record_path (optional): dotted path to the list, e.g. results.jobs. Omit when the response is the list.
  • count_ratio (default 0.5): current count must be ≥ baseline × ratio.
  • min_count (default 0): absolute floor.
  • headers (optional): auth, etc.

How it works

  • On each schedule (0 */6 * * * = every 6h, or workflow_dispatch for a manual run), it fetches each feed and computes a fingerprint: {top-level container, sorted record key set, record count}.
  • It compares against the last-known-good baseline committed to state/<id>.baseline.json — so runs are reproducible and you can git diff exactly what changed.
  • If any feed reports a problem, the step exits non-zero → the run turns red → your normal Actions notification fires.
  • Only when healthy does it commit the new baseline — it never “blesses” a broken feed as the new normal.

Run it locally

python3 watchfeed.py feeds.json /tmp/state     # JSON feed: no deps
python3 watchfeed.py feeds.yml  /tmp/state     # YAML feed: needs `pip install pyyaml`
python3 -m pytest tests/                        # offline test suite

Exit codes: 0 all healthy · 1 breakage detected · 2 config/usage error.

Who it’s for

  • Job-board operators and any team that consumes a feed or API and needs to know immediately when it regresses.
  • Anyone who wants a cheap, self-hosted, git-diff-able data health check without standing up a monitoring stack.
